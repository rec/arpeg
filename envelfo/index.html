Connecting arpeg and enveLFO¶

Install the Python extra with uv sync --extra envelfo in this checkout, or pip install 'arpeg[envelfo]' for a published package. The optional module is arpeg.envelfo; ordinary arpeg imports do not import the enveLFO runtime. Rust hosts use the separate arpeg-envelfo crate. Neither event core depends on the other. This integration has no NumPy, audio engine, Python bindings, MIDI device dependency, or new executable. The Rust MIDI player is used only as a device-free development dependency in its conformance tests. The Python MidiPlayer examples additionally require arpeg[midi,envelfo] (or both extras with uv); the bridge itself remains independent of meedee and MIDI devices.

Contract and scheduling phases¶

The host owns time, tempo/transport observations, MIDI delivery, and observation cadence. A bridge connects one arpeg hit output to a Patch-owned Envelope's start command, and maps named Patch outputs to breath, bend, or pressure. Other arpeg events do nothing. Multiple same-time hits retain their input order and receive distinct Envelope command ordinals. The bridge does not route note-end to release automatically: a rhythmic hit Envelope is not a voice gate.

An arp lane is distinct from an expression lane such as breath or bend. Player events carry a 1-based MIDI channel, but the bridge triggers on every supplied hit without filtering its channel. To trigger from one arp lane, filter events by event.channel before calling receive. Returned expression controls are broadcast to the configured owning arp lanes; they have no per-arp-lane target.

For each scheduled timestamp:

  1. Deliver input and transport changes using arpeg's existing ordering. Supply any tempo change through schedule's tempo argument, not the one-call set_tempo method, so an attack at that boundary stays unrealized.
  2. Call player.schedule for that timestamp, then drain its port events. This advances the note engine but does not construct or send the scheduled MIDI.
  3. Deliver its hit events to bridge.receive at their exact host seconds.
  4. Call bridge.observe once after all same-time hits, supplying the explicit next-delivery time for Threshold edges.
  5. Pass the returned expression controls to player.realize. Due releases and replacement note-offs precede the fresh entry controllers and note-ons. Continuing notes on other channels receive the new samples once per channel; released or muted notes receive no extra controllers. Deliver the returned MIDI in order.

All same-time hits are delivered before one observation, preserving the existing shared-channel expression policy. Each attack at that boundary uses that sample; no per-note observation or extra clock advancement is implicit. The ordinary advance method runs the same schedule/realize path without new samples.

Do not substitute an event's beat position for host seconds. Supply Python's tempo_map or Rust's per-child ClockMapping when the Patch has beat-clock children. Apply the same accepted tempo/transport observations to both mappings. The default seconds clock keeps advancing while arpeg is stopped; a beat clock follows its host's elapsed-beat mapping. A transport seek relocates arpeg but does not implicitly reset every enveLFO child. Send explicit Patch commands when a particular Envelope or LFO should reset, release, or seek.

The original after-note-on decision has been replaced by this explicit two-phase path. Newly triggered expression is now available to instruments that latch controllers at note-on. An Envelope still starts at its defined initial value, which may legitimately be zero; the bridge does not advance its attack to invent a nonzero onset.

Do not use player.control between these phases. Supply expression samples to realize instead. Other player mutations require realization first; stop is the exception, cancelling unsent attacks and releasing only actually realized notes. Draining port events is allowed between phases. Note lifecycle events are produced during realization, so drain again afterwards if the host consumes note_start/note_end events. A cancelled scheduled hit does not undo any enveLFO commands the host has already delivered.

A host may wake irregularly, but must still process every scheduled boundary chronologically. Advancing the player far ahead and then feeding old hits back at the wake-up time loses their timing and cannot be repaired by this bridge. Merge arpeg deadlines, enveLFO event/next-delivery deadlines, external input, and the chosen expression-observation schedule. LiveArpeggiator.next_deadline includes every arp lane, queued strum attack and owned release. Strum attacks after the parent hit still need their own scheduling/observation boundaries. realize rejects fresh samples if its pending batch spans multiple attack boundaries. A single fractional boundary remains valid when the host wakes at the next representable clock tick; note and decision beat timestamps remain exact. An invalid ownership/range control leaves the batch available for correction. This is an explicit host composition, not a second autonomous scheduler or a fixed-rate polling loop. Drain port batches after operations and honor exhausted; never silently drop an over-capacity batch. Feedback, density, gate, and selection mappings are not implemented here. There is no same-time feedback loop.

Python¶

Prepare the independent LFO and hit-triggered Envelope as one standalone Patch:

from fractions import Fraction

from envelfo import patch
from ufor import envelfo
from ufor.segments import Segment

from arpeg.envelfo import EnveLFOBridge

definition = patch.PreparedPatch(
    envelfos={
        "wave": envelfo.LFO(rate=1, shape="triangle", center=0.5, depth=0.5),
        "attack": envelfo.Envelope(
            start="event",
            retrigger="reset",
            segments=[Segment(duration="250 ms", to=1)],
        ),
    },
    outputs={"breath": "wave", "accent": "attack"},
)
bridge = EnveLFOBridge(
    definition=definition,
    state=patch.initial_patch(definition, Fraction(0)),
    hit_target="attack",
    expression={"breath": "breath", "pressure": "accent"},
)

Configure the player's profile with expression = { lanes = { breath = "envelfo", pressure = "envelfo" } }. Bend retains its current or recorded ownership. Input controllers continue to be captured; an enveLFO-owned lane does not overwrite the captured source data. The player rejects controls for lanes not explicitly owned by enveLFO.

At a host-selected boundary, with player, at_ns, and next_delivery supplied by that host:

player.schedule(at_ns)  # Or schedule(at_ns, tempo=bpm) at a tempo boundary.
at = Fraction(at_ns, 1_000_000_000)  # relative to the Patch's chosen host epoch
batch = player.take_events()
if batch.exhausted:
    raise RuntimeError("arpeg output capacity exhausted")
events = []
for event in batch.events:
    events.extend(bridge.receive(at, event))
observation = bridge.observe(at, next_delivery=next_delivery)
events.extend(observation.events)
messages = player.realize(observation.controls)

The bridge returns all named floating-point values as well as rational ArpeggiatorControl samples. Python converts the signal's decimal representation to a Fraction; Rust approximates the floating signal with its existing rational type. Arpeg's existing normalized-range checks and MIDI quantization still apply. An out-of-range sample fails before committing the bridge observation. Host event times remain exact rationals, never floating-point approximations.

Save player.model_dump_json() and bridge.model_dump_json() together at the same phase boundary, including between scheduling and realization if needed. The player retains its pending engine output; do not schedule it a second time. Restore with their respective model_validate_json methods. The bridge includes Patch definitions, child state, pending deliveries, and retained values. Resupply the same host clock mapping after restoration. Any messages or returned events already collected but not yet delivered belong to the host and must also be saved or drained consistently.

Rust¶

Build a normalized envelfo_core::patch::Patch with the same wave LFO, attack Envelope, and breath/accent outputs. Set Envelope start to Start::Event and retrigger to Retrigger::Initial. Then initialize:

```rust,ignore use arpeg_core::ports::InputPort; use arpeg_envelfo::EnveLFOBridge; use envelfo_core::{patch::Seconds, time::Time};

let state = definition.initial(Time::ZERO, "patch", 0, None, &Seconds)?; let mut bridge = EnveLFOBridge::new( definition, state, "attack".into(), vec![ (InputPort::Breath, "breath".into()), (InputPort::Pressure, "accent".into()), ], )?;

player.schedule(at_us, None)?; // Or Some(bpm) at a tempo boundary. let batch = player.take_events(); assert!(!batch.exhausted); let at = Time::new(at_us, 1_000_000)?; for event in &batch.events { let events = bridge.receive(at, event, &Seconds)?; // Deliver or retain returned enveLFO events in the host. } let observation = bridge.observe(at, next_delivery, &Seconds)?; let messages = player.realize(&observation.controls)?; ```

Rust bridge continuation uses Clone, including pending Patch deliveries. There is no serialized Rust bridge/player snapshot or cross-language snapshot interchange in this slice. The host must preserve its arpeg and delivery state alongside the bridge using its own existing continuation mechanism.

The complete normalized Rust construction is in the composition tests. Run cargo test -p arpeg-envelfo --locked without Python or MIDI devices. Run uv run --frozen pytest test/test_envelfo.py for Python. Both consume one shared trace, covering expressive controllers between notes, tempo changes, stop/start, seek, and final release. The independent pre-note wire cases cover all three expression lanes, overlapping replacements, boundary tempo changes, muted updates and captured phrases with recorded/current lane ownership.
